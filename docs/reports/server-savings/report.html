Does the mcp-for-kibana server make an AI agent's Kibana work cheaper and faster?

mcp-for-kibana is an MCP server: it gives an AI agent ready-made Kibana tools in place of Kibana's raw REST API. To measure what it saves, Claude Code did four Kibana tasks with and without the server, 288 runs in all, measured with Honeycomb. With the server, a run cost 51 to 71% less and took 34 to 60% less time, depending on the model, and every run passed its checks. The savings come from what the server keeps out of the model: without it, the agent read back 10 to 19 times more tool output per run.

The setup

Same agent, same tasks, two ways to reach Kibana

Claude Code ran four Kibana tasks with no person involved: build a dashboard and alert rule on web-log data, the same on flight data, change an existing dashboard and rule, and look up facts about them. Each task ran with Haiku, Sonnet and Opus 5.5, in both setups, 12 times: 288 runs. Each run sent one trace to Honeycomb; 287 arrived, and every number below covers those 287.

With the server Claude CodeHaiku, Sonnet or Opus 5.5 mcp-for-kibana serverKibana tools such as describe_data_view, create_dashboard, create_alert_rule, update_panel Kibana
Without Claude CodeHaiku, Sonnet or Opus 5.5 Shell and curlwith Kibana's API reference as files to read Kibana REST API

After every run: a checker reads Kibana back and scores the result, Kibana is reset, and the run's trace goes to Honeycomb. The trace holds Claude Code's model and tool calls, the server's own spans and one summary span with the run's model, setup, task, cost, time and checks.

Method

How the numbers were calculated

Honeycomb queries, the per-model figures and attribute names

Every number on this page is a Honeycomb result: a query (COUNT, SUM, AVG, P25, P50, P75, HEATMAP or a formula), a BubbleUp or a trace view. All queries run over 2026-10-12 17:10–20:10 UTC on the summary spans named efficiency.run, one per run; the server's spans (tools/call …) and Claude Code's spans sit under them in the same trace. 287 of the 288 runs reached Honeycomb; the missing one is an Opus run with the server on the change task (query).

Cost and time per run. For each model, task and setup, Honeycomb's P50 of the run's list-price cost (study.total_cost_usd) and wall-clock seconds (study.wall_s), over 12 runs. With 12 runs, P50 reports one of the two middle runs. P25 and P75 from the same query give the spread.

Per-model figures. For each task, the with-server P50 divided by the without P50. Per model, the geometric mean of the four task ratios, so each task weighs the same; “% less” is one minus that. The table shows every step.

Where the savings come from. AVG per model and setup over all four tasks, because P50 pooled across tasks jumps between the build and look-up runs. Model time is a calculated field, study.duration_api_ms ÷ 1000; other time is study.wall_s minus it.

Totals and counts. two SUMs of cost, one per setup; checks as the formula SUM(study.checks_passed) ÷ SUM(study.checks_total); COUNT of runs. Figures 11 and 12 are Honeycomb's own HEATMAP charts; the BubbleUp tables list Honeycomb's percentages for a selected region against the rest.
