What does an AI agent cost, how long does it take, and why? A worked example in Honeycomb

A team running AI agents wants to know four things: what each run costs, how long it takes, where the cost and time go, and whether a change would help. Here is a worked example that answers all four: Claude Code doing Kibana work, with and without a purpose-built MCP server, a tool server the agent calls instead of Kibana's raw REST API. With the server, runs cost {{COST_LO}} to {{COST_HI}}% less and took {{TIME_LO}} to {{TIME_HI}}% less time, and every run passed its checks. Honeycomb showed where the cost and time go: without the server, the agent reads back {{AVGB_LO}} to {{AVGB_HI}} times more tool output on average ({{MEDB_LO}} to {{MEDB_HI}} times by median).

Terms used below. A trace is the timeline of one run; a span is one step in it, and each run's summary (cost, time, result) is one span. A heatmap plots every run at once. BubbleUp lists what a selected group of runs has in common, compared with the rest. Median is what Honeycomb calls P50.

Questions 1 and 2 · cost and time per run

Cheaper and faster on every task

Claude Code ran four Kibana tasks with no person involved: build a dashboard and alert rule on web-log data, the same on flight data, change an existing dashboard and rule, and look up facts about them. Each ran with Haiku, Sonnet and Opus 5.5, in both setups, 12 times: 288 runs, judged by a script that read Kibana back.

Question 4 · would a change help?

Heatmaps show every run; BubbleUp shows what the odd ones share

BubbleUp compares a selected region with all other runs, attribute by attribute, and ranks what is over-represented in the selection. It finds what the selected runs have in common; it does not show what caused them.

{{FIG9}} {{BU1}}

The expensive band is the experiment's design: all 12 Opus web-logs builds and all 12 Opus flights builds without the server, and no other run (count query). Figure 1 already shows those cells as the costliest. BubbleUp's other high-ranked attributes, such as “no Kibana tool calls”, restate the setup. Open this BubbleUp in Honeycomb.

{{FIG10}} {{BU2}}

Here BubbleUp found something the medians did not show. Slow runs were much more likely to contain a failed tool call, mostly an HTTP 4xx error from Kibana's API. With-server runs had no failed calls, so the fair comparison stays within builds without the server: {{FAIL_SLOW}}% of the {{N_SLOW}} slow runs had a failed call, against {{FAIL_REST}}% of the other {{N_REST}} (from the run records). The 60-second cut was chosen by eye; run times are continuous around it. Our reading, supported by Figure 3: without the server the agent learns the API by trial and error, and each error costs another model turn. Open this BubbleUp in Honeycomb.

What Honeycomb added

  • Any attribute, no re-export. Each run summary carries 161 attributes; any one can be grouped or filtered in the next query.
  • Every run on one picture. The heatmaps (Figures 9, 10) showed the separate cost band and the slow tail.
  • The ranking done for you. BubbleUp ranked 122 attributes for a selection in one step, and surfaced the failed-call pattern.
  • Agent and tool server in one trace. Claude Code's spans and the MCP server's spans join on the run's trace (Figures 3, 11), so the server's own time per tool sits beside the model's.
For a client

How to reproduce this for a client

Two ways to use it. As a benchmark, the way this experiment did: run a design choice both ways, with an outcome check, before shipping it. In production: put the same summary span on live runs, with whatever success signal the team has (task completed, user accepted), and watch cost per run and failure rate.

Where every number comes from

Figures 1, 2 and 4 to 14 are Honeycomb query results over 2026-10-12 17:10–20:10 UTC. Each figure links its query and names its panel on the board {{B1}} or {{B2}}; each panel shows the same query and time range as its figure. 287 of the 288 run summaries reached Honeycomb; the missing one is an Opus run with the server on the change task. Honeycomb's sums and averages equal the committed run records without that run.

The headline percentages, the script's ratios and intervals, the 288-run totals ($5.09 and $14.49) and the median byte ratios come from the committed analysis and run records in the mcp-for-kibana repository; so do the within-build failure rates, the telemetry request counts and byte sizes.
